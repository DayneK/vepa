# Performance pass — 2026-10-04 (Gem: "< 10 fps at ~300 particles on the test build")

Method: built app (`VITE_BASE=./ npm run build`), Chrome 154 headless (`/usr/bin/google-chrome --disable-gpu`), TIDAL_BLOOM
preset, canvas2d renderer, 1400×900, rAF frame times over 5–6 s after a 4 s warm-up, CDP CPU profile of the main thread,
worker `TICK_COMPLETE.tickDuration` captured by wrapping `Worker`. Harness: `/workspace/perf/profile.mjs` (box only).

## Root cause

The test build (and GitHub Pages) is served **without COOP/COEP headers**, so `crossOriginIsolated` is false and
`SharedArrayBuffer` is unavailable. `canUsePhysicsWorker()` then returned false and **the full solver ran on the main
thread inside requestAnimationFrame**: one 70–500 ms solve per frame. The dev server (`vite.config.js`), the e2e suite and
the renderer benchmark all set COOP/COEP, and `bench:multiplex` runs in Node worker_threads with the light preview law
set, so none of them ever exercised this path.

## Fix (PERF-1, 09925f0)

Without SharedArrayBuffer the physics worker now runs in **copy mode**: each `TICK` transfers a copy of the live particle
slice (`count × stride` floats) and `TICK_COMPLETE` transfers it back; the main thread adopts it before population and
intelligence run. Same solver, same tick sequence; golden parity unchanged (13 scenarios).

## Results (single sim, no cross-origin isolation, i.e. the test-build situation)

| Population (start → live) | Before fps | After fps | Sim ticks/s before → after | Main thread busy before → after |
|---|---:|---:|---:|---:|
| 300 → ~480 | 11.8 (p50 83 ms) | 60 (p50 16.7 ms) | 12.5 → 13.3 | 99.9% → 51% |
| 1000 → ~1070 | 4.9 (p50 200 ms) | 60 (p50 16.7 ms) | 5.7 → 5.7 | 99.9% → 62% |
| 2500 | 2.1 (p50 467 ms) | 57 (p50 16.7 ms) | 2.8 → 2.2 | 100% → 94% |
| Multiplex default preset | 60 | 60 | — | 50% → 44% |

Before, per frame at 300: physics ≈ 74 ms (solver JS), canvas raster ≈ 10 ms, GC ≈ 3.5 ms, UI/DOM < 0.1 ms, field < 1 ms.
After: render ≈ 7–14 ms native canvas raster + 1–3 ms JS, GC < 0.2 ms, worker messaging < 0.1 ms; the solver runs in the worker.

## Remaining limits (decisions for Gem)

1. **Sim tick rate** is bound by the reference solver's per-pair cost with the 41 TIDAL_BLOOM laws: ≈ 3.5 µs per
   neighbour pair (Node: 300 → 37 ms, 480 → 75 ms, 1070 → 250 ms per tick). The profile is flat (no single law > 3%);
   compatibility evaluation is the largest share (~25% of solve). A faster tick needs either a behaviour change
   (smaller default pairwise budget / quality scaling — changes golden hashes) or a multi-day bit-identical solver
   restructuring.
2. **Canvas2D raster at 2500+** (two arcs per particle incl. a 2.4× halo) keeps the main thread ~94% busy in software
   raster; GPU-accelerated canvas on real hardware is much cheaper. Making PixiJS the default or a sprite-based halo
   would change default visuals.
